# Tax-aware exit layer: rates, synthetic lots, and what's real vs curated

This document explains the taxation model added to the trade-plan optimizer in
[backend/app/tax_rules.py](../backend/app/tax_rules.py) and
[backend/app/tax_lots.py](../backend/app/tax_lots.py): what it computes, what
is real vs synthetic, and the fund-level caveat every reader of a tax figure
in this app should know.

## The fund-level caveat

Under Section 10(23D) of the Income Tax Act, income of a notified Indian
mutual fund — including capital gains realized when the fund sells a
security — is **exempt from tax at the fund level**. Tax liability shifts to
the investor only when they redeem their units, not when the fund trades
inside the scheme. So a real HDFC Flexi Cap or ICICI Pru Large Cap does **not**
pay STCG/LTCG when it sells a stock.

The capital-gains layer in this app is a **deliberate modeling choice** (a
PMS/taxable-account framing) to demonstrate a genuinely useful decision
pattern — preferring low-tax exits and harvesting losses — that a fund
manager evaluating "which holdings are more/less suitable to sell" would
still care about in an advisory or non-exempt context. What *is* real
regardless of the 10(23D) exemption is transaction friction: **STT, brokerage,
and exchange charges apply on every sell**, and those are modeled with real
current rates.

## Real vs synthetic, at a glance

| Data | Real | Synthetic |
|---|---|---|
| STCG rate (20%), LTCG rate (12.5%), Rs 1.25L exemption, 12-month holding threshold | Yes — current statutory rates | |
| STT (0.10% sell), brokerage, exchange charges | Yes — market-standard rates | |
| Lot cost prices | Yes — actual `monthly_close` on the lot's acquisition date, from `data/processed/final/stock_macro_monthly_target.csv` | |
| Lot acquisition dates, how many lots per holding, and which lots are "loss" lots | | Yes — no disclosure exposes a fund's purchase history, so these are generated |

Because cost prices are drawn from real historical closes, a lot's unrealized
gain/loss reflects the stock's actual price path — the synthetic part is only
*when* the fund is assumed to have bought, not *at what price it would have
paid on that date*.

## Rates (FY 2025-26)

Configured in [data/processed/tax/tax_rates.json](../data/processed/tax/tax_rates.json)
and loaded by `tax_rules.py` (with embedded fallbacks), so a future budget
change is a config edit:

| Parameter | Value |
|---|---|
| STCG rate | 20% (holding < 12 months) |
| LTCG rate | 12.5% (holding >= 12 months) |
| LTCG annual exemption | Rs 1,25,000 (applied once at plan level) |
| STT on sell | 0.10% of sell value |
| Stamp duty on buy | 0.015% of buy value |
| Brokerage + exchange charges | ~0.033% |

## Synthetic tax lots

Generated by `tax_lots.generate_lots()` and persisted to
[data/processed/tax/tax_lots.csv](../data/processed/tax/tax_lots.csv) via
`python -m app.tax_lots` (1,247 lots across the 356 real holdings, as of the
last generation):

- 2–5 lots per holding, deterministic per ISIN (same lots every restart).
- At least one lot placed >12 months back (guaranteed LTCG) and, where the
  position is large enough, one placed <12 months back (guaranteed STCG).
- ~18% of holdings get a lot deliberately placed at the highest real close in
  the trailing 36 months, so genuine loss lots exist for tax-loss-harvesting
  demos.
- `data_v2.py` loads the persisted CSV at startup via `attach_tax_data()`
  (same pattern as `curate_security_metadata`); a holding missing from the
  file falls back to the identical deterministic generator.

Each holding gains: `tax_lots[]`, `avg_cost`, `unrealized_gain_pct`,
`stcg_shares`, `ltcg_shares`, `effective_tax_rate_pct`, `txn_cost_rate_pct`,
`tax_source`.

## How it changes the optimizer's decisions

- **`optimize_sell`** ([backend/app/optimizer.py](../backend/app/optimizer.py)):
  the objective changes from minimizing forfeited expected return to
  minimizing `(horizon-scaled expected return) + exit tax + transaction cost`
  per rupee sold. Loss positions carry a *negative* tax rate, so the LP
  naturally prefers to liquidate them (tax-loss harvesting) over realizing
  gains on a short-term winner with the same forecast return.
- **Horizon scaling**: the expected return is scaled by `horizon_days / 21`
  before comparing against tax, because tax is paid once but a predicted loss
  repeats every period — a persistently losing stock is sold even if its exit
  tax is high.
- **`optimize_rebalance`**: adds a convex tax penalty on the sell side only
  (`exit_cost @ pos(w_cur - w)`, clipped at 0 so it never rewards realizing a
  loss twice — that reward already lives in `optimize_sell`), so rebalances
  don't needlessly churn high-tax winners.
- **Rules path** (`_funding_sells`): ties on portfolio weight are broken by
  preferring the lower-tax exit.

## Plan output

Every SELL order carries a `tax` breakdown (`stcg_gain`, `ltcg_gain`,
`stcg_tax`, `ltcg_tax`, `stt`, `txn_costs`, `total_tax`, `effective_rate_pct`,
`lots_consumed`), attributed **least-tax-first** across the holding's lots.
The plan-level `tax_summary` and `summary.est_total_tax_cr` /
`summary.tax_drag_bps` / `summary.stcg_share_pct` roll this up, and
`optimization.tax_saved_vs_naive_cr` compares the tax-aware solve against a
tax-blind one for storytelling.

## Policy guardrails

`policy.py` adds (WARN/ESCALATE only — the human still decides):

- **TAX-DRAG**: WARN above 60 bps of sell proceeds, ESCALATE above 150 bps.
- **TAX-STCG-SHARE**: WARN when >50% of sell value comes from short-term lots.
- **TAX-HOLD**: WARN when a stock with a negative forecast return was kept
  only because its exit cost exceeds the expected loss over the horizon,
  including the date its remaining STCG lots turn LTCG.

## Known gaps (not addressed here)

- No wash-sale rule (the app doesn't model reinvestment/repurchase).
- The synthetic lots are attached at read time, not persisted per-fund
  transactionally — a real system would need lot state to survive executed
  trades across plans.
- The SBI Nifty 50 ETF AUM parses incorrectly (`docs/trade-plan-data-requirements.md`
  and the review notes both flag this); its rupee-scale tax figures inherit
  that distortion until the parser is fixed.
